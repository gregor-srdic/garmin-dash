font heights rather than tuned by hand.

### Premise correction

The request framed all three devices as "smaller screen". The 850 is not:
420×600 at 269 ppi is more pixels than the 1040 and close to the 1050. These are two
unrelated problems and should be two separate pieces of work.

## 2. Why both devices are broken today

Every currently supported device is ~1.67 aspect ratio. The layout in `DashView.mc:405-580`
derives its **vertical** positions from **width**:

```
radius     = minDim * 0.33          // minDim == width on all portrait Edge devices
centerY    = radius + topBarH + trackWidth + offset
elapsedY   = 2 * radius + topBarH/2 + xtinyH + 1
cadenceY   = 2 * radius + topBarH * 2
panelTop   = centerY + radius * 0.5 + topBarH * 2
```

…while the footer anchors to **height**:

```
footerY    = height - largeH - xtinyH
panelH     = footerY - panelTop - height * 0.01
```

Compress height without compressing width and the middle of the screen marches into the
bottom of it. `panelH` is the shock absorber, and it runs out.

### edge850 (420×600)

Falls into the `screenWidth >= 400` branch (`DashView.mc:858`) and inherits the **1050
profile** — fonts sized for an 800 px screen on a 600 px screen.

Geometry: `radius` 138.6, `topBarH` 48.6, `trackWidth` 34.9, `centerY` 217.

| Collision | Detail |
|---|---|
| top bar ↔ gauge crown | top bar ends y≈87, gauge crown starts y≈61 |
| elapsed ↔ cadence row | elapsed spans 323–384, cadence spans 379–440 |
| panel band overflow | 128 px available; small(33)+numberHot(109)+xtiny(21)+medium(38) ≈ **201 px** needed |

These numbers are exact — the 850's font heights are known.

### edge840 / edge830 (246×322)

Falls into the `screenWidth < 260` branch (`DashView.mc:910`), already labelled
"Edge 840 / 540", which is nothing but a copy of the 1040 offsets and has never been built.

Geometry: `radius` 81, `topBarH` 26, `trackWidth` 20, `centerY` ≈ 135.

| Collision | Detail |
|---|---|
| elapsed ↔ cadence row | elapsed ≈194–227, cadence starts 206 |
| cadence ↔ panels | cadence runs to ≈239, `panelTop` = 227 |
| panel band overflow | **≈41 px** available, ≈110 px needed |

**This branch is the trap.** Adding `edge840` to `manifest.xml` compiles and renders, so it
looks like it works — it just produces stacked, unreadable text. Since the 840 has identical
font metrics to the 1040, no combination of offsets fixes it. Content has to be removed.

## 3. Plan

### Phase 0 — Instrument — **DONE**

A temporary `System.println` of `dc.getWidth()` / `dc.getHeight()` / `dc.getFontHeight()` for
all nine fonts and `dc.getTextWidthInPixels()` for the worst-case strings, run under
`monkeydo` on 830, 840, 1040, 1050 and Explore 2. Results in section 1 and in `CLAUDE.md`.

Worth the half day on its own: it invalidated the font-metric premise this plan was built on
(above) before any layout work started.

### Phase 1 — edge850 — **DONE** (code committed, needs visual sign-off)

> **Estimate was wrong.** This phase originally said "step the speed and panel fonts down
> one, ~1 day, no content change". Measured against the code's real formulas, the 850 on the
> 1050 profile overflows by ~160 px and a one-step font reduction recovers only ~30 px of
> that. The row fonts had to come down too **and** the gauge had to shrink. No content was
> dropped, but the layout is visibly less dramatic than the 1050's.

What was actually done:

1. `manifest.xml` — added `<iq:product id="edge850"/>`.
2. `resources-edge850/strings/strings.xml` — `deviceType` = `edge850`.
3. Two new profile keys, threaded through all five existing profiles at their current values
   so no shipped device changes by a pixel:
   - `:rowValueFont` — font for top bar / elapsed time / cadence row / footer values.
     Was hardcoded `FONT_LARGE` in six places.
   - `:gaugeRadiusFactor` — speed gauge radius as a fraction of screen width. Was hardcoded
     `0.33`, and written twice (once for `radius`, once inside the `centerY` expression);
     those are now coupled.
4. edge850 profile branch, placed **before** the `screenWidth >= 400` check:
   `rowValueFont` LARGE→MEDIUM, speed THAI_HOT→NUMBER_MEDIUM, panels HOT→NUMBER_MILD,
   unit labels SMALL→TINY, gauge radius 0.33→0.25, plus `elapsedTimeYOffset` +20 and
   `cadenceLineYOffset` +30 to redistribute the reclaimed space.

Verification:

- `monkeyc` builds clean for edge850, edge1050, edge1040, edge1030, edgeexplore2.
- Geometry checked by replaying `onUpdate`'s formulas against the 269 ppi font metrics.
  Calibration: the **shipped 1050** carries two text-box overlaps (4.3 px and 0.1 px), so
  that is the practical tolerance. edge850 on the 1050 profile: seven overlaps, worst 20 px.
  edge850 on the new profile: two overlaps, worst 1.7 px — tighter than the 1050 baseline.
  `panelH` recovers from 132 px to 200 px.
- **Simulator sign-off 2026-07-28: looks fine, no offsets changed.** `elapsedTimeYOffset`
  (+20) and `cadenceLineYOffset` (+30) stand as tuned.

Deferred: `edge550` (same 420×600 panel, buttons instead of touch) — one manifest line and
one resource dir once the 850 is signed off.

### Phase 2 — Refactor before touching the 840 — **DONE** (needs simulator sign-off)

Twenty absolute pixel offsets per device works for one aspect ratio. It will not survive two.
**Do not skip this to reach the 840 faster** — it is what keeps the ongoing maintenance cost
bounded.

Scope note: item 3 was deliberately limited to the *mechanism*. Building a compact band stack
before Phase 3's content decisions (section 4, and the open questions in section 6) are made
would be unexercised code with no device selecting it.

What was done:

1. `onUpdate` reduced to palette setup, layout resolution and five calls:
   `drawTopBar` → `drawSpeedGauge` → `drawMiddleRow` → `drawPanels` → `drawFooter`, in the
   same z-order as before. `drawMiddleRow` covers both text rows (elapsed time, then
   cadence/gear/grade) since they move together.
2. All geometry pulled out into `computeFullLayout(dc)`, which returns the y-bands and gauge
   geometry as a Dictionary. No draw function derives its own position any more — the two
   places that separately hardcoded `0.33` are already coupled from Phase 1, and the
   `footerY` / `panelTop` / `panelH` chain is now computed in one place instead of being
   threaded through the middle of the draw code.
3. `computeLayout(dc)` dispatches on the new `:layoutVariant` profile key. All six profiles
   carry `:full`; `:compact` is declared and documented but has no branch body yet — that is
   the single edit point Phase 3 fills in.
4. Layout is cached in `mLayoutCache` and recomputed only when the dc dimensions change; the
   per-frame palette moved to member fields. A draw pass now allocates nothing, which also
   helps the 830 watchdog concern in Phase 4. (`mLayout` is not available as a field name —
   `WatchUi.View` already declares a protected one.)

Verification:

- Builds clean for all 7 shipped products: 1050, 1040, 1030, 1030 Plus, 1030 Bontrager,
  850, Explore 2.
- Refactor is intended to be pixel-neutral. The sequence of `dc.clear` / `dc.setPenWidth` /
  `dc.drawText` / `dc.drawArc` calls is identical to `main` (34 calls, same order), and every
  moved expression preserves its operand types — including the integer divisions
  `topBarH / 2` and `barW / 2`, which would silently shift positions if promoted to float.
- **Simulator sign-off 2026-07-28: looks fine.** Same standing as Phase 1.

### Phase 3 — edge840 / edge830 — **DONE** (needs simulator sign-off)

Scope decisions taken at implementation time: Option B's cut list as written; fixed layout,
no `compactSecondary` setting; edge530 / edge550 not included.

What was done:

1. `manifest.xml` — added `<iq:product id="edge840"/>` and `<iq:product id="edge830"/>`.
2. `resources-edge840/` and `resources-edge830/strings/strings.xml` — `deviceType` values.
3. The dead `screenWidth < 260` profile branch (a copy of the 1040 offsets, `:full`, never
   built) replaced by the one `:compact` profile, selected on `deviceType` with the width
   test kept as a safety net for the 530 / 540. It carries six keys rather than twenty:
   `:speedFont` NUMBER_THAI_HOT, `:barValueFont` NUMBER_MILD, `:rowValueFont` SMALL,
   `:unitLabelFont` TINY, `:gaugeRadiusFactor` 0.40, `:speedYOffset` 0.
4. `computeCompactLayout(dc)` — bands laid out from the screen edges inward from measured
   font heights, with the speed gauge taking the remainder and shrinking below
   `:gaugeRadiusFactor` if either the band height or the screen width cannot take it. One
   profile serves both devices despite the 10 px font-metric gap, because nothing in the
   path is an absolute offset.
5. Four compact band functions (`drawCompactTopBar` / `…SpeedGauge` / `…Bars` / `…Footer`),
   dispatched in `onUpdate` on the layout's `:variant`. They share no code with the `:full`
   band functions, so the shipped devices cannot regress.

Content, per Option B: clock + temperature (no labels — two values on a row do not need
them); speed gauge, 12 segments, no AVG/MAX pair; HR and power as horizontal zone bars,
mirrored so both fill away from centre; elapsed time / cadence / grade / distance in
content-spaced rather than even columns, since elapsed time is three times the width of the
others. The two adaptive touches from section 4 are both in: no gear readout at all, and
when there is no power meter the right bar becomes a cadence bar and the footer's cadence
slot shows ascent instead.

Verification:

- Builds clean for all 9 products: 1050, 1040, 1030, 1030 Plus, 1030 Bontrager, 850, 840,
  830, Explore 2.
- Geometry read back out of the running layout under `monkeydo` on both devices rather than
  derived on paper. No band collides with another and no text overruns its column on either
  device; tightest clearances are the 830's footer GRD/DIST gap at 12.6 px and its KMH label
  against the gauge's lower arc ends, which do not overlap horizontally. For calibration the
  shipped 1050 carries a 4.3 px text-box overlap, so this is comfortably inside tolerance.
- Draw calls per frame: 12 `drawArc` + 20 `fillRectangle` + 16 `drawText`, against `:full`'s
  44 `drawArc`. This is the Phase 4 watchdog item for the 830, so that item is already met.
- **Simulator sign-off 2026-07-28: looks fine on both devices, `:gaugeRadiusFactor` left at
  0.40.** The gauge still does not use its whole band, so there is room to grow it later if
  it reads as small on hardware.

Deferred: `edge530` / `edge540` (same panel, buttons instead of touch) — one manifest line
and one resource dir each, and the width test already routes them to `:compact`.

### Phase 5 — edge550 / edge540 / edge530 — **DONE** (routing verified on device profiles)

Unblocked by Phase 4's sign-off and implemented the same day, option A. No new layout work:
each of the three is a pixel-identical sibling of a device Phases 1–3 already cover.

#### Parity evidence

Compared the `ww` font set in each device's `simulator.json`, not the spec sheets. Font
families **and point sizes** match exactly within each pair:

| Pair | Text fonts | Number fonts | Res | ppi | Datafield mem | Watchdog |
|---|---|---|---|---|---|---|
| 530 / 830 | `FNT_ROBOTO_CONDENSED_13/20/22/26/41` | `FNT_DEJAVU_FITNESS_26/30/40/50` | 246×322 | = | 131072 | 2500000 |
| 540 / 840 | `DejaVuSans_Cd_SemiBold_WGL4` @ 4.8818 … 13.4249 | `Garmin_Roboto_Bold` @ 13.901 … 26.5382 | 246×322 | 156 | 131072 | 2500000 |
| 550 / 850 | `DejaVuSans_Cd_SemiBold_WGL4` @ 5.3079 … 15.5697 | `Garmin_Roboto_Bold` @ 16.1231 … 31.1469 | 420×600 | 269 | 131072 | 2500000 |

So the Phase 0 font-height table already covers all three — no re-measurement needed, and any
offset tuned on a parent during Phase 4 applies to its sibling automatically.

The hardware difference is buttons instead of touch (`isTouch: false`). Irrelevant to a data
field: the project has no `InputDelegate`, `onTap` or `onKey` anywhere, and
`DashApp.getInitialView()` returns views only.

#### The 550 is the one that needs care

530 and 540 are already routed correctly by the `screenWidth < 260` safety net in
`DashView.mc:1636`, so they would work off a bare `manifest.xml` line with `deviceType` =
`default`.

**The 550 would not, and would fail silently.** The 850 branch (`DashView.mc:1535`) is keyed
on `deviceType.equals("edge850")` alone, so a 550 with the default string falls through to
`screenWidth >= 400` (`DashView.mc:1565`) and inherits the **1050 profile** — exactly the
~160 px overflow in section 2. It compiles and renders, so it looks like it works.

Two ways to wire it:

- **A — deviceType, as every other device does.** `resources-edge550/strings/strings.xml`
  with `deviceType` = `edge550`, added to the `edge850` branch condition. *Recommended*:
  consistent with the documented deviceType-first ordering, and keeps the
  one-resource-dir-per-product invariant that makes this trap visible.
- **B — route by geometry.** Narrow the 1050 branch to
  `screenWidth >= 400 && screenHeight >= 700` so any 420×600 panel falls through to the 850
  profile with no `deviceType` at all. Fewer files, but it contradicts the branch ordering
  documented in `CLAUDE.md` and makes the chain harder to reason about.

#### What was done (option A)

1. `manifest.xml` — three `<iq:product>` lines.
2. `resources-edge530/`, `resources-edge540/`, `resources-edge550/strings/strings.xml`. The
   550's is load-bearing; the other two are for explicitness — the width net covers them
   today, but leaving them on `default` means a future reordering of the branch chain breaks
   them silently.
3. `DashView.mc` — `deviceType.equals("edge550")` added to the 850 branch, `edge540` /
   `edge530` to the `:compact` branch. No new profile keys, no new geometry, no new draw code.

#### Verification

- All 12 products build clean.
- **Routing read out of the running app, not derived on paper.** A temporary
  `System.println` of the resolved `deviceType`, dimensions, `:layoutVariant` and
  `:gaugeRadiusFactor` was run under `monkeydo` on all six devices, then removed:

  | Device | deviceType | w×h | variant | gaugeRadiusFactor |
  |---|---|---|---|---|
  | edge550 | `edge550` | 420×600 | `:full` | **0.25** |
  | edge850 | `edge850` | 420×600 | `:full` | **0.25** |
  | edge530 | `edge530` | 246×322 | `:compact` | 0.40 |
  | edge540 | `edge540` | 246×322 | `:compact` | 0.40 |
  | edge830 | `edge830` | 246×322 | `:compact` | 0.40 |
  | edge840 | `edge840` | 246×322 | `:compact` | 0.40 |

  `0.25` is the discriminator that matters: it exists only on the 850 branch. Had the 550
  fallen through to `screenWidth >= 400` it would have reported `0.33`. Each sibling resolves
  to byte-identical geometry to its parent.

- Note: static inspection cannot verify this. `Rez.mcgen` carries only resource *ids*, and
  every `.prg` embeds all the `deviceType` string literals regardless of device, because they
  are the `.equals()` operands in `initDeviceProfile`. Running it is the only check.

## 4. Content adaptation for 246×322

Roughly 150 px of content has to go.

### Option A — shrink everything

Keep all 18 values, smaller fonts throughout.

**Rejected.** At 156 ppi on a 2.6" screen this stops being glanceable on rough road, which
defeats the purpose of the field.

### Option B — prioritise *(recommended)*

Drop the review-time data from the always-on view: AVG/MAX speed, AVG HR, AVG power,
elevation, ascent, calories. These are checked afterwards, not mid-effort.

```
┌────────────────────────────┐
│  12:34            21.4°    │  clock + temp          ~26px
├────────────────────────────┤
│        ╭─────────╮         │
│         ◜ 32.4 ◝           │  speed arc + value    ~150px
│        ╰── KMH ──╯         │
├────────────────────────────┤
│ ▉▉▉▉░░ 148  │  245 ░░▉▉▉▉  │  HR + PWR, zone bars   ~56px
├────────────────────────────┤
│ 1:24:07   87   2.4   12.6  │  time cad grade dist   ~44px
└────────────────────────────┘
```

Speed stays the hero. Both zone-coloured gauges survive — they are Dash's visual identity.
The bars go horizontal: cheaper vertically than arcs and easier to read peripherally.

### Option C — rotating secondary slot

One field cycles temp → elev → ascent → cal every ~4 s.

Maximum density, but cycling fields are polarising and it costs a timer. Offer as a setting,
not a default.

### Adaptive touches worth adding regardless

- Show the **gear** readout only when Di2 data is actually present. It is `"--"` for most
  riders — reclaim the slot for temp.
- Reuse the existing `mHasPowerData` trick so the right gauge falls back to cadence, freeing
  the cadence slot in band 4 for distance.

### New setting

Add a `compactSecondary` enum property letting users pick what fills the last band-4 slot
(distance / ascent / calories / avg speed). Cheap, and it defuses most "you removed my
metric" complaints.

## 5. Risks

- **Store submission.** Each product needs its own build and a re-submission.
- **CIQ 3.3.1 on 830/530** will exercise the fallback paths for real: no
  `getFunctionalThresholdPower` (→ the `ftp` property), likely no
  `Activity.Info.ambientTemperature` (→ the `SensorHistory` path). Both are already guarded
  correctly in `DashView.mc`, but they have not been exercised on hardware this old.
- **Two layouts to maintain.** Every future feature lands twice. Phase 2 bounds this cost.
- **Sequencing.** Ship Phase 1 on its own first. The 850 is a far better return per day of
  work and is independently releasable.
